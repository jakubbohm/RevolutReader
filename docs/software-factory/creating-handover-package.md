# Creating the Software-Factory Handover Package

**Status:** inventory kept current while the project runs · **Package:** not built yet

At the end of the project (roadmap step M8, Decommissioning, or earlier if the user asks), RevolutReader hands what it learned over to the user's Software Factory in a package. The handover is a process, not a file copy ([lessons.md R-22](lessons.md)): this file says where the package goes, what goes into it and how to build it.

## The target

The **Software Factory** will be a repository of its own (not created yet, 2026-11-07). It holds:

- **the knowledge:** for every setup topic, the question, the options, which constraints favour which option, and the recommended default;
- **what each answer produces** in a new project;
- **a "set up new project" skill.** The owner runs it inside the factory. It creates the new project's folder outside the factory and runs the tools that start it (e.g. `git init`, the codebase-memory index). Then it asks the owner the factory's questions one by one: repository host, cloud, hosting, database, Aspire, sign-in, and so on. Each answer produces its part of the project:
  - files of any kind: CLAUDE.md, conventions, ADRs, Claude skills, agents, hooks and memory, scripts, real code, settings;
  - entries added to shared files: `.gitignore`, `package.json`, and the like;
  - tools run;
- **a "software factory update" skill,** copied into every project, that sends newly gained general knowledge back to the factory.

The factory is first built by consolidating two sources: DoseUp's catalog (`D:\source\jakubbohm\DoseUp\docs\software-factory.md`, the factory's unfinished first version) and this package. That consolidation is the user's next project after RevolutReader. If the factory already exists at handover time, the package goes in through the factory's own intake instead, along the lines of [§ Intake](#intake).

## What the package contains

- [lessons.md](lessons.md): every lesson, with RevolutReader's constraint set.
- The reusable artifacts listed in [§ Inventory](#inventory), as they are at handover time.
- A README for the package ([§ Building the package](#building-the-package), step 5).

Not included:

- [divergences.md](divergences.md): it stays with the project.
- Skills and commands installed by tools (OpenSpec, Aspire): the tools install them.
- Artifacts that only repeat DoseUp's.
- This project's ADRs and archived change notes: the lessons carry their findings and link to them with permanent links ([§ Building the package](#building-the-package), step 4).
- This file: its reusable part is [lessons.md R-22](lessons.md).

- **template:** the factory copies it, with RevolutReader's names and values replaced by placeholders, and the set-up skill produces it in a new project;
- **example:** it shows how a lesson was applied here; the factory keeps it as it is, next to the lesson.

A file that fits only this project is not listed.

Keep it current: a step that creates or substantially changes a reusable artifact adds or updates its line here in the same session, with its kind. The description says what a new project reuses, not how the file changed.

## Building the package

1. **Complete the lessons and check the inventory.** Fill every `TBD` in [lessons.md](lessons.md) ([§ Entry format](lessons.md#entry-format) there). Every listed artifact still exists. Follow the links in lessons.md and add anything reusable that is missing from the list.
2. **Collect.** Copy lessons.md and the listed artifacts into a folder outside the repository (`revolutreader-handover-<date>/`), keeping their repository paths.
3. **Clean.** No secrets, keys or tokens, and no bank data (balances, amounts, counterparties, transaction texts, account identifiers): `secrets/` and `evidence/` folders never go in. In templates, replace RevolutReader's names and values (project, resource and app names, client and subscription IDs, the dates of this project's approvals) with placeholders that say what goes there. Examples keep theirs; they show a real case.
4. **Fix the links.** A link to a file of this repository that the package does not carry (an ADR, an archived change's design notes, the roadmap) becomes a permanent GitHub link at the handover commit: `https://github.com/jakubbohm/RevolutReader/blob/<commit>/<path>`. The repository is public, so these links keep working after the files leave it. Links between files the package carries stay relative.
5. **Write the package README:** what is inside (one line per kit and the lessons it belongs to), the source repository and commit, the date, the target ([§ The target](#the-target)), and the intake below.
6. **Hand it over:** in the factory's consolidation session if the factory does not exist yet, otherwise in a session in the factory's repository. Back here, set **Package** in this file's header and **Handover** in [lessons.md](lessons.md) to `done <date> → <target>`, and record it in `pm/progress.md`.

## Intake

The factory decides under its own rules. This is how the package is meant to go in, so that the factory keeps one question per topic, each with its options:

1. **A lesson that answers a question the catalog already asks** (*Divergence*, e.g. R-23 and DoseUp F-85): RevolutReader's answer joins that question, as a new option or as a second project behind an existing one. It brings the constraints that picked it and the condition that reverses it. The topic never gets a second question.
2. **A lesson where RevolutReader changed its own mind** (*Reversal*): a note on its question, saying what was tried first and why it was dropped. Reversals are the factory's best training data (DoseUp F-23).
3. **A lesson that asks something the catalog never asked** (*New*): a new question in the matching topic.
4. A lesson of several kinds takes each route.
5. **RevolutReader's constraint set** goes next to DoseUp's, so the factory can tell which constraint decided which answer.
6. **The inventory's artifacts** go where the factory keeps what the set-up skill produces, linked from the options that produce them.
