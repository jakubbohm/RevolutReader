# Software Factory — Lessons from RevolutReader

**Status:** knowledge deposit, collected while the project runs · **Started:** 2026-11-04 · **Handover:** not yet ([creating-handover-package.md](creating-handover-package.md))

What the user's future "software factory" (a tool that interviews the owner of a new project and recommends answers from accumulated knowledge) should learn from RevolutReader. The main catalog lives in DoseUp: `D:\source\jakubbohm\DoseUp\docs\software-factory.md`, entries F-1 … F-92 as of 2026-11-04. At the end of the project this file goes into the handover package together with the artifacts it describes, for the standalone Software Factory ([creating-handover-package.md § The target](creating-handover-package.md#the-target)). Where RevolutReader itself runs a cut-down version of a lesson, the project's side (what it gives up, when it switches back) is in [divergences.md](divergences.md).

## What goes in

Only three kinds of entries — everything else is already in the DoseUp catalog:

- **Divergence:** RevolutReader deliberately answered a question differently from DoseUp.
- **Reversal:** RevolutReader reversed one of its own earlier decisions (recording reversals is the factory's best training data — DoseUp F-23).
- **New:** a question DoseUp never faced (e.g., a regulated third-party API with request limits).

Add an entry in the same change or session that makes the decision. The project's own docs stay the authority (ADRs, conventions); an entry here links to them and never replaces them. The default an entry recommends is always the full version, the one that fits a real, long-lived project; a cheaper answer RevolutReader took appears only as an exception, with the constraint that allows it, and gets an entry in [divergences.md](divergences.md).

## RevolutReader's constraint set

Every answer below was reached under these constraints. An entry's *Generalizes* line names the constraint that decided it, so the factory can tell which constraint flips which answer:

solo developer · ~2-month operating period, then decommissioned · **speed of delivery is the top priority for the app**, never for what it hands to the software factory (R-1) · 3 use cases, essentially one screen · a handful of pre-approved users · read-only access to one real bank account through a regulated third-party API with request limits · Azure, with free-tier resources shared across the owner's projects · one deployed environment.

## Entry format

The DoseUp catalog's shape, plus a topic and what the factory's set-up skill produces ([creating-handover-package.md § The target](creating-handover-package.md#the-target)):

```markdown
**R-<n> · <Question, phrased for any project>?** *(<Divergence | Reversal | New> — relates to DoseUp F-<x>, if any)* · *Topic:* <section of DoseUp's catalog, e.g. G. Delivery>
Options: <option> · <option> · … (with trade-offs, briefly).
DoseUp: <its answer, one line> — omit for New entries.
RevolutReader (<link to the ADR / convention>, <date>): **<the answer>** — <why, briefly>.
*Setup produces:* <what the set-up skill does for RevolutReader's answer>.
*Generalizes:* <the reusable rule> — **and the constraint that would reverse it**.
```

- **The length follows the decision.** A big decision may carry bullets under its answer and a long *Setup produces*. A small convention can be three lines, with the rule itself in place of a question, e.g.:

  ```markdown
  **R-<n> · Command validation is synchronous and checks the command's format, never business rules** *(New)* · *Topic:* D. API & contract
  RevolutReader (<link to the convention>, <date>): <why, in a sentence, if it isn't obvious>.
  *Setup produces:* the rule in the backend conventions.
  ```

- **A quick entry is enough at first.** When there is no time for the details, record the title line and the answer in a sentence, so the lesson is not forgotten. Write `TBD` for every line not settled yet, the *Topic* and *Setup produces* included. Every `TBD` is filled before the handover ([creating-handover-package.md § Building the package](creating-handover-package.md#building-the-package), step 1).
- **Complete before the handover:** the id line with its *Topic*, RevolutReader's answer, and *Setup produces*. The other lines appear when they have something to say:
  - **Options** only when the owner should choose. An entry without them is a rule the factory applies without asking.
  - **DoseUp** only for a Divergence.
  - ***Generalizes*** is left out only when the answer already is the reusable rule and no known constraint reverses it.
- **Topic:** a section of DoseUp's catalog (A Product discovery, B Platform & language, C Architecture, D API & contract, E Data & auth, F Testing, G Delivery, H Formatting & static quality, I AI-assisted workflow, J Configuration & secrets), or a new topic name when none fits.
- ***Setup produces*:** what the set-up skill does when a new project picks RevolutReader's answer: files of any kind, linked to [the inventory](creating-handover-package.md#inventory) where they are listed; entries added to shared files (`.gitignore`, `package.json`, …); tools it runs; manual steps it guides the owner through. What the other options produce comes from the projects that pick them.
- **No project history:** no issue or PR numbers, no record of who asked for what and when, no measurements from one deployment. Those stay in the ADR or design notes the entry links to. The entry keeps what the next project needs to decide and to set up.
- Ids are `R-1`, `R-2`, … in order of recording, never reused or renumbered. They are shared with [divergences.md](divergences.md): a decision with both a lesson and a divergence keeps the same id in both files, and a new entry in either file takes the next free number.
- Ecosystem facts (versions, prices, limits, licenses) carry the date they were verified.
- Plain language; no RevolutReader-internal codenames without a link.
- Links to the project's files are fine. The handover package carries the reusable ones ([creating-handover-package.md § Inventory](creating-handover-package.md#inventory)) and turns links to the rest into permanent GitHub links ([§ Building the package](creating-handover-package.md#building-the-package), step 4).

**R-1 · How high is the architecture bar?** *(Divergence and Reversal — relates to DoseUp F-42)* · *Topic:* I. AI-assisted workflow
Options: architecture first, even at the cost of speed · speed first, but flag works-vs-correct gaps · no explicit rule · a split bar: the product's bar chosen per project, the full bar always for the work that feeds a software factory.
DoseUp: architectural quality is the project's highest priority.
RevolutReader (CLAUDE.md § Working rules, 2026-11-04; [workflow.md § 10 — The quality bar](../conventions/workflow.md#the-quality-bar-2026-11-08), 2026-11-08): **a split bar: speed of delivery first for the app, no shortcuts in software-factory work** (these lessons, the reusable kits, the handover). For the app, Claude still says when "works" and "correct" differ, then recommends the fastest sound option; the user decides. A cut-down inside a reusable kit is the user's decision, recorded as a divergence that names the full version. During the project that note is enough; the full version is built and proven at the handover, so the factory's template is always the full one (R-22). What the app gives up: [divergences.md R-1](divergences.md).
- **Reversal (2026-11-08):** speed first was at first the bar for everything, so it also governed the lessons and the kits this project hands to the factory. A shortcut there becomes every later project's default, so speed first was narrowed to the app.

*Setup produces:* the working rule in CLAUDE.md § Working rules: two quality bars, the product's own (here speed of delivery first, with every gap between "works" and "correct" named and the fastest sound option recommended) and the full bar for software-factory work, with what counts as such work in the workflow conventions next to the software-factory files of R-22 (inventory: Claude working rules); the project's divergences file, where each cut-down answer records what it gives up and when to switch back.
*Generalizes:* the bar follows the project's "why" (DoseUp F-4): showcase/learning goals buy architecture-first, a short-lived tool buys speed-first. Reverses when the system must outlive its first purpose or others will maintain it. When a short-lived project also feeds a reusable factory, the bar splits: the product takes the project's bar, and the factory always takes the full one, because the factory's answers outlive the project and become other projects' defaults. The factory work need not slow the project down: notes that name the full version are enough while the project runs, as long as the handover turns them into the full solution.

DoseUp: always a prose proposal (solution, trade-offs, alternatives, recommendation); never clickable option menus.
RevolutReader (CLAUDE.md § Working rules, 2026-11-04): **prose for big decisions, menus acceptable for quick confirmations** — efficient for confirming decisions inherited from an earlier project in bulk (here 40 from DoseUp), with a "more details" option on each.

DoseUp: automated changelog, semver tags and GitHub Releases.

DoseUp: Microsoft.FeatureManagement; every flag ships with a removal task.

**R-5 · What stays manual when infrastructure is code?** *(Divergence and Reversal — relates to DoseUp F-53)* · *Topic:* G. Delivery
Options: everything manual (guided portal steps) · everything in IaC · IaC with an explicit manual list.
DoseUp: hand-authored Bicep is the only definition of Azure; never portal or ad-hoc CLI.
RevolutReader (docs/conventions/workflow.md § 5, 2026-11-04): **Bicep + Azure Deployment Stacks (removed resources get deleted) for everything the project owns; manual only for what cannot be automated** — subscription access, the Entra application registration, the CD identity's trust (bootstrap), shared resources and access to them, and hand-provisioned secret values. Reversal: the first roadmap draft had made all Azure setup manual; the owner corrected it.

*Generalizes:* ask "which resources outlive or are shared beyond this project?" — e.g., a free tier that exists once per subscription (Cosmos DB) must be shared, so it cannot belong to one project's stack and is referenced as `existing`. Everything project-owned goes into the stack, which also makes decommissioning a single stack deletion. Reverses toward all-manual only for throwaway experiments.

**R-6 · Where do work items live?** *(Divergence — relates to DoseUp F-77, F-79, F-80)* · *Topic:* I. AI-assisted workflow
Options: GitHub issues/milestones/board · plan and status files in the repo.
DoseUp: GitHub issues, milestones and a project board; open decisions as `decision` issues.
RevolutReader (docs/conventions/workflow.md § 9, 2026-11-04): **`pm/roadmap.md` + `pm/progress.md` in the repo**; decisions in ADRs. What the project gives up: [divergences.md R-6](divergences.md).
*Setup produces:* `pm/roadmap.md` and `pm/progress.md` (inventory: Project management), the CLAUDE.md rule that every session reads both first, and the ADR folder for decisions.
*Generalizes:* with a fixed plan of ~20 steps, one session per step and a short life, repo files beat a tracker. Reverses with a growing backlog, several contributors, or a need for a board view.
*Amended 2026-11-08 (the user, when C7 was split; [workflow.md § 9](../conventions/workflow.md#9-project-management)):* the files stay the plan, the status and the decision trail, and **every piece of planned work also gets a GitHub issue** by default, linked both ways with its roadmap entry and closed by the PR that finishes it; the user may skip it for a single item. The files alone gave no link target for PRs and no place to track work outside a session; the issue holds only the goal, so the detail keeps one home. A board view is still not used.
*Weighed the same day and not chosen for this project (the user):* moving each step's detail into its issue (the issue's description as the current state, edited in place; comments as the history), leaving the roadmap a thin index and `pm/progress.md` one line per step. Measured on 2026-11-08: the files every session reads at start (roadmap, progress, CLAUDE.md) had grown to about 34,000 tokens, mostly the narrative of finished steps, while `pm/` added only 5–7 KB to a feature PR (the OpenSpec change's own files were 20–30% of it). For the factory: keep the always-read files small from the start, and put a finished step's story in its PR and closing comment rather than in the status file.

**R-7 · How is UI designed before it is built?** *(Divergence, then Reversal and New — relates to DoseUp F-41)* · *Topic:* I. AI-assisted workflow
Options: a mockup + handoff for every UI-heavy change · only for key screens · none · a design system before the first frontend code, plus one canvas of every screen, changed before the code.
DoseUp: every UI-heavy change gets a Claude Design mockup + handoff.
RevolutReader ([docs/conventions/workflow.md § 8](../conventions/workflow.md#8-design), 2026-11-05): **a design system made before the frontend foundation, and one Design with every screen and state made before the first screen is built. A visual change starts in the design and the code follows. Coding sessions read both by link.**
- **Reversal:** the first plan (2026-11-04) had one mockup, for the account screen only, because the app has essentially one screen. It was reversed before any UI existed: a design system costs one prompt, and the sign-in, account and notification screens share its components and states.
- **New (verified 2026-11-05):** Claude Design moved into Claude as artifact types ("Design System", "Design"); the standalone claude.ai/design closes on 2026-12-14, so a handoff flow built on the standalone site (DoseUp F-41) has to move. Claude Code reads an artifact file by file through its link, signed in as the owner. Here the design system arrived with a Tailwind v4 theme file, a tokens file, reference React components and formatting helpers. No export or handoff bundle is needed.
- **Gotcha (verified 2026-11-05 in the Design type's own documentation):** a Design canvas keeps a copy of the design system, pinned to the version it was made from, and the copy never updates by itself. After changing the design system, ask each canvas to update its copy. This is also the reason for one canvas holding every screen instead of one artifact per screen: one copy to update, one set of sample data. Each artboard is still its own file and can be changed alone.
- **Gotcha (verified 2026-11-05 in the canvas's files):** the update replaces only the copied files (components, their styles, the tokens file). What the canvas made itself stays as it was: text typed into an artboard, and here its own CSS copy of the tokens, written because the design system shipped none, which every artboard takes its colours from. A plain "update" would miss a changed colour. So each design-system change ends with two prompts: the design-system session lists what it changed, old → new, because it knows the owner's steering; the canvas updates its copy and applies the list to what it made itself ([workflow.md § 8](../conventions/workflow.md#8-design) has both prompts).
- **New (2026-11-05): the coding agent keeps the change loop in mind, not the owner.** A design change crosses three places: the owner asks Claude Code, which writes the design-system prompt; the design system lists what it changed; the canvas applies the list; the same list goes back to Claude Code, which compares the artifacts with the code. The owner runs this only now and then and expects to forget it, so an always-loaded Claude rule ([.claude/rules/design.md](../../.claude/rules/design.md)) makes Claude Code walk the owner through it whenever a visual change comes up. It is a rule in the repository rather than a personal memory, so it travels with the kit.
- **Gotcha (2026-11-05):** a subagent with a fixed tool list, here the test-first implementer (read, search, edit, shell), cannot open Claude artifacts, so it would build the UI from the written design alone. The orchestrating session reads the design files into its scratchpad and hands the implementer their paths with each UI group ([tdd-apply § 0](../../.claude/skills/tdd-apply/SKILL.md)).
- The prompt asked for what makes the result usable in code: tokens named for the CSS framework's theme, the UI-library primitive under each component, one icon set referred to by name, the target device's viewport and safe areas, the UI language's number and date formats, and invented sample data only.
- **New (2026-11-06): three kinds of design files** ([workflow.md § 8](../conventions/workflow.md#8-design)). The files the app ships (the icon, images, logos) are copied byte for byte and committed, and generated sizes come from a committed config run by hand. Tokens, components and formats are translated into the app's own code. Reference code, screens, sample data and guidelines are never copied. "Nothing from the design goes into the repository" was too strict: the app can't ship an icon it doesn't hold. Gotcha: a repository that forces LF line endings on a frontend folder treats images there as text too, and a PNG's bytes get rewritten on commit. Mark them binary ([README.md § Formatting](../conventions/README.md#formatting)).

*Setup produces:* the design section of the workflow conventions and the always-loaded rule `.claude/rules/design.md` (inventory: Design); the design-file handover in `tdd-apply` § 0 (inventory: Test-first workflow); `npm run icons` for the files the app ships and the `.gitattributes` rule that keeps images binary (inventory: Frontend). Manual: the owner makes the design system and the Screens design in Claude, with the prompts from the design section.
*Generalizes:* design the system before the first frontend code. Tokens and components are cheapest to get right before code depends on them, and every later screen design inherits them. Keep one canvas of screens and change it before the code, so the design never lags behind. Have the design system ship every file a canvas loads, a CSS file of its tokens included, so an update carries every change; end every design-system change with its own list of changes for the canvases to apply. Write the loop into an always-loaded agent rule, so the coding agent walks the owner through it each time, and make sure every agent that writes UI code can actually see the design. Reverses toward no design for a throwaway prototype, or for a UI made only of a framework's stock components.

**R-8 · How do you read a regulated bank API that limits unattended requests?** *(New)* · *Topic:* Third-party APIs
Options: unattended reads only, within the quota, served from stored data · live reads forwarding the present user's real context, plus a background job within the unattended quota · ask the provider first whether the present user's reads may count as attended.
RevolutReader ([ADR-0001-bank-data-access](../adr/0001-bank-data-access.md), 2026-11-04): **live reads with the signed-in user's real PSU headers when the user opens or refreshes the view; a background job without PSU headers 4 times a day (the PSD2 default for unattended requests, which Revolut counts per account, endpoint and consent); the provider is not asked.** The main user is the owner's daughter, not the account holder the bank treats as the PSU; the owner's position is that she reads on his behalf. The provider's FAQ says to send the headers of whoever triggers the fetch, but not whether that person must be the account holder. Without the provider's explicit confirmation it is an accepted risk: the owner accepts being cut off and keeps the risk low with strict rules on when PSU headers are sent. Stored data refreshed every 6 hours was rejected because the view must match the bank's own app. What the project gives up: [divergences.md R-8](divergences.md). *(2026-11-06: the background job was replaced by a check the owner's iPhone triggers, with the phone's PSU headers: R-45.)*
*Setup produces:* an ADR with the provider's request limits, the decision on when the user's headers (PSU headers) are sent, and the accepted risk; the read trigger (present user or unattended) as a required parameter of every read in the adapter. Adapter template: TBD (the adapter is not in the inventory).
*Generalizes:* the quota applies only to requests made without the user present, so the "user present" signal must carry the real values of the person actually present, only on requests they trigger directly, never on background work. Whether someone other than the account holder counts as present is the provider's call, not a technical question; without their confirmation it is an accepted risk. Reverses toward asking the provider first, or toward stored data within the unattended quota, when losing access would be costly (long operation, many users, a business) or when the provider's terms explicitly exclude acting on the account holder's behalf. *(Limits verified 2026-11-04 for Revolut via Enable Banking.)*

**R-9 · How do you keep a bank account's transaction history when the bank serves only a rolling window?** *(New)* · *Topic:* E. Data & auth
Options: show only the bank's rolling window (e.g. 90 days; no database) · store everything fetched · store only settled transactions and re-read pending ones live.
RevolutReader ([ADR-0001-bank-data-access § Decision](../adr/0001-bank-data-access.md#decision), item 6, 2026-11-04): **store only settled transactions, keyed by the aggregator's stable entry reference, from the date the history starts to matter. Read the balance and a short recent window live. Download the older history once, right after an approval.** Revolut returns more than 90 days only within 5 minutes after an approval. Pending transactions can still change, be cancelled, or get a new ID once settled. The rolling window was rejected because the owner needs the history from a fixed date for good.
*Setup produces:* the one-time history download right after an approval (`create-session.ps1 -HistoryStart`, inventory: Personal bank access) and a table of settled transactions keyed by the provider's entry reference: since C7b (2026-11-09) the store behind its port with a Table adapter (R-26) and the one-time import of the downloaded history (R-69).
*Generalizes:* settled transactions are immutable facts worth storing; pending ones are a live view, never stored. Capture older history in the window right after an approval, because it may not come back without the account holder present. Before choosing, ask the owner from which date the history matters: a fixed start date that is about to fall out of the window makes it urgent. Reverses toward the rolling window when nobody needs history older than the bank serves, which also removes the database. *(Revolut and Enable Banking behaviour verified 2026-11-04.)*

**R-10 · How do you keep a short-lived app restorable after it is decommissioned?** *(New)* · *Topic:* Operations & observability
Options: nothing (decommissioning is final) · write a rebuild guide at the end · keep a register of every expiring approval and secret from the first step, and write the rebuild guide from it before decommissioning.
RevolutReader ([docs/operations/expiring-approvals.md](../operations/expiring-approvals.md), the roadmap's reinstatement-guide step, 2026-11-04): **a register of every expiring approval and secret with its expiry, how you notice and how to restore it, kept current by every step that creates or renews one; plus a reinstatement guide written before decommissioning**, assuming every secret, approval and cloud resource is gone. The owner expects to reactivate the app later. Stored transactions are not exported at decommissioning: a reinstated app downloads the history again in the 5 minutes after its new approval. Third-party approvals with short, fixed terms (here a 30-day account link and a 180-day bank session) are easy to forget and need the account holder present to renew.
*Setup produces:* the register `docs/operations/expiring-approvals.md` (inventory: Operations guides); the roadmap rule that every step creating or renewing an approval or secret updates it; a reinstatement-guide step before decommissioning.
*Generalizes:* collect restore knowledge as you go, because reconstructing it at the end misses the hand-made steps. For each external approval, record who must be present to renew it and what data can be recovered afterwards (here, older transaction history only right after a new approval). Reverses toward "nothing" only when the app will certainly never return. If it is torn down, decide before deletion whether to export the data that cannot be fetched again.

**R-11 · How does a personal app get read access to the owner's own bank account without a banking licence?** *(New)* · *Topic:* Third-party APIs
Options: become a licensed account information provider (not realistic for an individual) · a commercial contract with a bank-data aggregator (company verification, volume-based pricing with a monthly minimum) · the aggregator's free mode for the owner's own accounts · unofficial screen scraping or shared bank credentials (against the bank's terms, fragile, unsafe).
RevolutReader ([ADR-0001-bank-data-access § Context](../adr/0001-bank-data-access.md#consent-validity-and-pricing-q5), [spikes/enable-banking/README.md](../../spikes/enable-banking/README.md), 2026-11-04): **Enable Banking's restricted production mode.** A production application becomes active once the owner links their own account in the Control Panel. It is free, limited to linked accounts, and allowed "solely for evaluation purposes or for the personal use of private individuals"; the Control Panel account must belong to the account holder. Costs accepted: registration still demands a privacy URL, a terms URL and a data protection email (placeholders work, since restricted mode does not check them); the account link lasts only 30 days and needs the account holder in the bank app to renew; and data access still needs its own API session, up to the bank's maximum (180 days for Revolut).
*Setup produces:* the guided Enable Banking setup from the spike scripts: the restricted-mode application, the account link in the Control Panel, the API session (inventory: Personal bank access); entries in the expiring-approvals register for the account link and the session.
*Generalizes:* for a personal or family tool reading the owner's own accounts, look for the aggregator's personal-use or own-accounts mode before anything commercial. Check three things first: whose accounts it covers, how long each approval lasts and who must be present to renew it, and the bank's request limits. Reverses toward a commercial contract when the app reads other people's accounts, serves customers or earns money. *(Enable Banking terms, FAQ and behaviour verified 2026-11-04.)*

**R-12 · Does the acceptance-test harness run the app inside the test process, or as the real running app?** *(Divergence — relates to DoseUp F-26)* · *Topic:* F. Testing
Options: in-process test host (WebApplicationFactory; the test replaces dependencies directly) · containers per dependency (Testcontainers) · the real running app, started by the orchestrator (Aspire testing harness).
DoseUp: Aspire harness only — the real graph of processes; tests that need to move the clock stay at unit level, because a fake clock cannot reach another process.
RevolutReader ([docs/conventions/testing.md § Acceptance-test harness](../conventions/testing.md#acceptance-test-harness-the-app-runs-inside-the-test-process), 2026-11-04): **in-process (TUnit.AspNetCore), as a project-only exception; the factory default stays DoseUp's real running app.** What the app reacts to lives outside it, and the tests must control it: the bank (to check which headers the app sends and that the background job stays within 4 calls a day), the clock (a check 4 times a day) and the sign-in key. In-process, each is a one-line swap, and no test needs a real secret. The app is a single API process. What the project gives up: [divergences.md R-12](divergences.md).
*Setup produces:* the in-process acceptance harness, `AcceptanceTest.cs` and `ApiFactory.cs` (inventory: Test-first workflow), with its section in testing.md; a divergence entry saying when to switch to the real running app.
*Generalizes:* DoseUp's default stands. Run in-process only as an exception, for a single-process app whose behaviour depends mostly on the clock and on third parties the tests have to fake anyway. Reverses to the default when the app runs as several processes whose wiring is itself a risk, or when the tests need no control over the clock or third parties.

**R-30 · Should outgoing HTTP clients retry by default, and how does a client that needs retries get them?** *(Divergence, with a Reversal — relates to DoseUp's ServiceDefaults)* · *Topic:* Third-party APIs
Options:
- the default: keep the Aspire template's standard resilience handler on every `HttpClient` (it retries 408, 429 and 5xx, for every method) · keep it and opt out per client · remove it and opt in per client;
- guarding "no default": the rule's text and review · a convention test that a plain client sends one request on a 503;
- a client that needs retries: a hand-written loop in the client · the resilience library's standard handler (retries, attempt and total timeouts, a circuit breaker) · one retry strategy of the library on that client alone;
- what it retries: the library's default (network failures, 5xx, 408, 429) · the same by status, without 429 · exactly what the client's own error classification calls transient;
- the numbers: the library's defaults (3 retries from 2 s) · a well-known SDK's · invented.

DoseUp: keeps the template default (`AddStandardResilienceHandler` in ServiceDefaults; checked 2026-11-05).
RevolutReader ([README.md § Backend code](../conventions/README.md#backend-code), [c001 design.md D5](../../openspec/changes/archive/2026-11-05-c001-add-backend-foundation/design.md), 2026-11-05; [c008 design.md D1–D11](../../openspec/changes/archive/2026-11-08-c008-add-bank-read-retries/design.md), 2026-11-08): **no default retries, guarded by a convention test; a client that needs retries gets one retry strategy of Microsoft's resilience library (`Microsoft.Extensions.Http.Resilience`, on Polly) on that client alone, retrying exactly what the client itself classifies as transient.**
- **Why no default:** whether to retry depends on what a client calls, so each client decides: a quota or a price per call (a retried 429 from Enable Banking would silently burn the 4 requests a day allowed without the account holder, [ADR-0001-bank-data-access](../adr/0001-bank-data-access.md)), whether the call can be repeated (the standard handler retries every method, so a lost answer to a push notification's POST sends it twice), an SDK's own retries (Azure SDK clients build their own pipeline, so the default never reaches them), and no stacked layers (a client with its own policy under a default sends up to 4 × 4 = 16 requests per call). Here a default would help no client and need two opt-outs, each invisible when forgotten. Microsoft's transient-fault guidance says the same: retry only when you know the full effect, prefer an SDK's built-in retries, avoid duplicated layers of retry, and beware repeating operations that are not idempotent ([Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/best-practices/transient-faults), read 2026-11-08).
- **The guard:** with the resilience package in the repository, one line in the service defaults would give every client retries. A convention test starts the app, sends one request through a plain `IHttpClientFactory` client to a local fake that answers 503, and expects exactly one request to arrive. A probe that adds the standard handler proves it fails, as build gates are proven (R-31).
- **Reversal, the bank client:** "the bank client never retries" was reversed before its first caller, because a one-off network failure or bank error would end as "bank unavailable" for a user who is waiting, and no one is there to try again when a phone triggers the read. Now it retries a present user's transient failures:
  - **one retry strategy, nothing else:** no circuit breaker, hedging, rate limiter or extra timeouts, which a handful of calls a day would never trigger. It sits on the HTTP client, so each request, e.g. a failed page, is retried alone;
  - **retried exactly when the attempt would end as "unavailable"**, by the client's own error classification, shared with the retry rule, so the rule and the final outcome can never disagree; rate limited, access expired and every other error never;
  - **the client's own timeout wraps the retries,** so the worst case per request stays what it was and a timed-out request is never repeated; a hung request is therefore not retried (accepted);
  - **requests a quota counts are never retried:** the client marks the requests of a user who is present, and an unmarked request is never retried, so the rule fails safe;
  - **each attempt reads the whole answer** inside the retry handler; otherwise a connection that breaks while the body comes in fails after the handler has returned and is never retried;
  - **the platform already resends** a bodiless request when the server closed an idle connection before any answer (.NET's HTTP stack, read in its source 2026-11-08), so the retries cover the rest, and a test of a broken connection must break after the answer has started or it proves nothing;
  - **the numbers are the Azure SDK's** (3 retries, waits from 0.8 s doubling; read 2026-11-08), not invented, with the library's random spread on each wait; a real outage then shows after about 6–8 s instead of under 1 s;
  - **`Retry-After` is followed only while its wait still ends before the request's own timeout;** otherwise the request fails at once instead of waiting for nothing;
  - **the first wait is a setting, zero in tests:** the library takes its clock from the app's services, so a fake clock that only a test moves would freeze any longer wait;
  - **the library's retry warnings stay, its line for every attempt goes** (a log level on its category), and a ready query lists the retries;
  - **an undocumented behaviour the retries rely on is probed once against the real service:** here, whether the provider accepts a page's continuation key a second time, with the account holder present and on present-user requests only. It does.
- **Rejected:** the template default with opt-outs, as DoseUp has it (every future client inherits retries nobody decided, and the bank client would start by removing them); a hand-written loop in the client (fewer parts, but a standard library exists); deciding by status alone (an unknown error code on a 5xx would be retried three times); a shorter timeout per attempt (it changes the setting's meaning and fails an answer a slow day would still give).

*Setup produces:* the service defaults without the standard resilience handler, and the convention test that guards it (inventory: Backend); the rule in README.md § Backend code that each client's retries are decided on their own. A client that needs retries: the resilience package referenced by that project alone, and one retry strategy on that client (inventory: Backend, the bank client's retries, an example).
*Generalizes:* retries are a decision per client, never a template default: what a client calls decides (quotas, rate limits or a price per call, whether a call can be repeated, an SDK's own retries), and a default stacks on every policy a client has of its own. Guard the rule with a test, because one line in the shared defaults undoes it. A client that needs retries gets one strategy on itself alone: it retries exactly what its own error classification calls transient, inside its own timeout, never a request a quota counts, with a well-known SDK's numbers, `Retry-After` honoured only within the timeout, and every undocumented provider behaviour it relies on probed once. Reverses to the template default when every downstream is your own idempotent service with no quota and no SDK of its own; add a circuit breaker to a client's strategy once its call volume is high enough for one to act. *(Versions, defaults and guidance verified 2026-11-08.)*

*Setup produces:* the image push and the anonymous-pull check in `deploy.yml`, and the `org.opencontainers.image.source` label in the Dockerfile (inventory: Deployment).
*Generalizes:* when nothing in the image is private, deploy a public image, and guard its visibility with a check that fails with the instructions instead of a step someone has to remember. A workflow's first push into a public repository may already come out public, though the docs say private; the check covers both. Reverses to a private registry pulled with the app's managed identity when the image holds anything private or public artifacts are not allowed.

**R-48 · How does a deploy prove that a scale-to-zero app really started?** *(New — relates to DoseUp F-53, its deploy smoke test)* · *Topic:* G. Delivery
Options: trust the deployment's success · request a health endpoint after the deploy · several revisions side by side with traffic labels and an automatic rollback · a full smoke-test suite against production.
RevolutReader ([workflow.md § 4](../conventions/workflow.md#4-cicd); c005 design.md D8; 2026-11-06): **three steps at the end of the deploy job.**
1. Wait until the app's latest revision is its latest ready revision, and check that this revision runs the image just pushed, by its commit tag.
2. Request `/health` and `/` at the public address, retrying for up to 3 minutes; the first request wakes the app. The time to the first answer goes into the run's summary, a free data point on the wake-up.
3. Confirm that the revision's running state is `Running`, not `Degraded`, `Failed` or `Stopped` (the values in the Container Apps REST spec, 2025-07-01). Azure also returns `RunningAtMaxScale` for a healthy revision at its maximum of one copy, a value the REST and SDK references do not list (they list Running, Processing, Stopped, Degraded, Failed and Unknown). The check accepts it next to `Running`; any other unknown state still fails after a minute.
- **Why:** with one revision at a time, a new revision takes the traffic once it has scaled to the old one's replica count and its probes pass ([Microsoft Learn: revisions](https://learn.microsoft.com/en-us/azure/container-apps/revisions), updated 2026-02-26). An app asleep at deploy time has 0 replicas, so the new revision may count as ready with nothing started: the stack succeeds and a broken version goes unnoticed until someone opens the app. That is a reading of the docs, not yet observed (below).
- **Why the image check in step 1:** if the new revision fails, the old one keeps the traffic, and `/health` alone would answer from the old version.
- **The probes matter for the wake:** a wake from zero waits for the startup and the readiness probe, so both run every 2 s. Container Apps limits a probe to 1–10 failures, a first delay of 1–60 s and a period of 1–240 s (REST spec 2025-07-01); the startup probe then allows the app about 20 s.
- The state is read through the core Azure CLI (`az resource show` with an API version), so the job needs no CLI extension.
- **On failure:** the job fails, GitHub emails the owner, and the fix is a revert PR. An automatic rollback was rejected as more moving parts than one user needs.
- **Observed (2026-11-06):** in the first two deployments the new revision already had a running copy before the first request, so the "ready with nothing started" case was not seen and the check's wait for a wake-up was not exercised. A sleeping revision's state reads `ScaledToZero`, also not in the references.

*Setup produces:* the checks after the deploy in `deploy.yml`, and the startup and readiness probes in the feature Bicep file (inventory: Deployment).
*Generalizes:* a deploy of a scale-to-zero app ends with real requests through the public address and a check that the revision answering is the new one. Match the platform's states against the known good values and fail on anything else after a short wait: the platform returns values its references do not list. Reverses to trusting the platform when the app always runs at least one copy and traffic moves only after the probes pass, and toward an automatic rollback when the minutes between a bad deploy and a revert matter.

**R-51 · How does an app keep an identifier that sits in an outgoing URL's path out of its logs and traces?** *(New)* · *Topic:* Operations & observability
Options: accept it · mask it in place (a custom HTTP-client logger, plus rewriting the URL tags on every trace activity) · silence that one client (its default HTTP logging removed, its requests left out of the exported traces) and log one line per call yourself · move the identifier out of the path (only when the API allows it).
RevolutReader ([c004 design.md D5](../../openspec/changes/archive/2026-11-07-c004-add-enable-banking-adapter/design.md), 2026-11-07): **silence the bank client, log one line per read, and guard it with a test.** Enable Banking's paths carry the account id (`/accounts/{id}/balances`), and the account id must never reach a log.
- **Why it leaks by default:** since .NET 9, `IHttpClientFactory`'s logging redacts only the query string; the path is logged as is, at `Information` ([Microsoft Learn, .NET 9 breaking change](https://learn.microsoft.com/en-ca/dotnet/Core/compatibility/networking/9.0/query-redaction-logs), read 2026-11-06). OpenTelemetry's HTTP-client instrumentation records the full URL of every outgoing call.
- **The fix:** `RemoveAllLoggers()` on that one typed client. Each request carries a request option that the HTTP-client trace filter in ServiceDefaults drops, so ServiceDefaults needs no bank address. The adapter writes one line per read instead: which read, who triggered it (never the user's values), HTTP status, the provider's error code, duration, pages, and how many transactions were left out. The trace id comes from the logging scope (the default host tracks it, checked on .NET 11 RC 3).
- **The guard:** an acceptance test runs real reads in the app copy against the fake bank. It collects every log message with its scopes, and every activity the app exports through OpenTelemetry's in-memory exporter. It fails if the account id, the session id, or the user's address or browser appears anywhere. It counts exported activities, not every activity: since .NET 9 the runtime's own HTTP activity carries the URL in-process, which is harmless as long as nothing exports it.
- **A false alarm to expect:** a fake server hosted inside the test process (WireMock.Net on Kestrel) exports its *own* server traces, with the path. The harness must silence the fake server's diagnostics, not weaken the guard.
- **A second false alarm, from the user's browser:** every server activity records the request's browser (`user_agent.original`, on by default in OpenTelemetry's ASP.NET Core instrumentation, checked on 1.20.1, 2026-11-07), and one app copy's tracing collects the activities of every app copy in the test process. A browser the guard shared with another test would fail it whenever that test sent the browser in a request to its own app copy at the same time. So the guard reads for its own made-up user, whose address and browser no other test uses.
- **Rejected:** masking in place. It keeps bank calls as their own trace steps, but it relies on two hooks that must catch every place a URL is recorded, now and after every library update.

*Setup produces:* the HTTP-client trace filter in ServiceDefaults (inventory: Backend); `RemoveAllLoggers()` on the sensitive client and one log line per call in the adapter; the telemetry guard test and the fake server's silenced diagnostics (inventory: examples).
*Generalizes:* an identifier in an outgoing URL's path leaks through default HTTP logging and tracing. Silence that client, log your own line with only what is safe, and keep a test that looks for the identifier in everything the app logs or exports. Reverses when the identifier is not sensitive, or when the provider accepts it outside the path; switch to masking when per-call trace steps for that dependency are worth the extra hooks.

**R-52 · Should the vault an app reads its secrets from be closed to the internet?** *(New — relates to R-50)* · *Topic:* J. Configuration & secrets

Reverses to roles alone for a short-lived app on a platform the vault doesn't trust, where only the app's identity and its owner hold a role.

**R-55 · An app with a login cookie sits on a hosting platform's shared domain: what does that domain's absence from the Public Suffix List change?** *(New)* · *Topic:* E. Data & auth
RevolutReader ([ADR-0003 § Decision](../adr/0003-sign-in.md#decision), items 6 and 7; c007 design.md D4; 2026-11-08): **`__Host-` cookies and the app's own rule refusing every write request from another site.**
- Browsers treat two addresses as the same site when they share a registrable domain, which the Public Suffix List defines. `azurecontainerapps.io` is not on the list (checked 2026-11-07), while `azurewebsites.net` and `azurestaticapps.net` are. So every other container app on the platform counts as the same site as ours.
- **What that breaks:** SameSite cookies stop protecting anything, because a sibling app's page is same-site: the browser sends a Lax cookie with its requests. A sibling could also plant cookies for the shared parent domain: a session cookie that signs the visitor in as someone else, or a sign-in round-trip cookie.
- **The answer:**
  - every cookie is named `__Host-…`, so the browser accepts it only from the app's exact host, set without a Domain and with Path `/`;
  - every POST, PUT, PATCH or DELETE under `/api` is refused unless the browser's fetch metadata says it came from the app's own page (`Sec-Fetch-Site: same-origin`) or from the user directly (`none`). Without fetch metadata, the `Origin` must equal the app's own origin, and a request with neither header passes (not a browser, so it has no cookie). Either header sent more than once is refused as ambiguous, inside the pure rule, so its table describes the whole decision. The sign-in return is exempt, because Microsoft posts it from another site by design.
- **Independent of the shared domain:** because the sign-in return takes form posts from any site (even an empty form ends in the handler's failure path), a cancelled or failed sign-in only redirects and never signs out. A top-level cross-site form post may delete even a Lax cookie, so a sign-out there would let any site sign the visitor out (issue #33, finding 3).
- **Checked by:** unit tests for every row of the rule's table, and acceptance guards that read the `Set-Cookie` attributes and send a sibling's sign-out request.

*Setup produces:* the cookie names and attributes in the sign-in registration; the rule as a pure function with its middleware (`src/RevolutReader.Api/Security/`, inventory: Backend) placed after authentication and before the endpoints; their unit tests and guards.
*Generalizes:* before relying on SameSite, check whether the hosting domain is on the Public Suffix List. If it isn't, every tenant is the same site: use `__Host-` cookies and a same-origin rule for every cookie-authenticated write. Reverses when the app has its own registrable domain, or the platform's domain is on the list; SameSite Lax plus the framework's own checks are then enough.

**R-56 · Does .NET 11's built-in forged-request protection cover a cookie-authenticated JSON API?** *(New — relates to R-55)* · *Topic:* E. Data & auth
RevolutReader (c007 design.md D4; 2026-11-08): **No, not reliably: the app adds its own rule for every write and keeps the built-in protection on.**

**R-60 · How does a client tell the API's own error answers apart when a proxy in the path answers with the same statuses?** *(Divergence — relates to DoseUp F-21)* · *Topic:* D. API & contract

- The types are listed in the API description: a problem class whose `type` is an enum written as the exact strings, so the generated client types name them and a type renamed on one side only fails CI's drift check or the frontend's type check. Without it, the strings are copied by hand into the backend, its tests and the frontend, and a one-sided rename shows only as the wrong message on the screen (the user, 2026-11-08, after C13's code review).
- The `type` is a relative full path because only the app's own screen reads it and needs nothing more than the label: a link would point every client at the source repository (the user, 2026-11-08, after C13's code review). A missing domain is no reason: an absolute address into the public repository's documentation needs none, and a `tag:` URI needs a domain or an email address the owner holds, which in a public repository is personal data. RFC 9457 (§ 3.1.1) recommends absolute URIs, allows relative ones with the full path, encourages ones that open a description, and asks consumers to compare the type after resolving it; the app's screen compares the string as sent. Cut-down in [divergences.md](divergences.md) R-60.

*Generalizes:* give a case its own problem `type` whenever its status could also come from something else in the path (a proxy, a gateway, a dev server), list the types in the API description, and let clients trust only the types. **The full version is an absolute `type` URI that opens the problem type's description (under the app's own domain, or a page of its published documentation), as RFC 9457 § 3.1.1 encourages** — reverses to a status alone only for a case whose status nothing else in the path can produce.

**R-71 · The test-first agents fill their context: with what, and how do they read less?** *(New — relates to R-7, R-16)* · *Topic:* I. AI-assisted workflow
Options: filter the test output, or hand test runs to helper agents · read the design by section · **read code the agent does not change as single symbols through a code graph** · lower the reasoning effort.
RevolutReader ([#67](https://github.com/jakubbohm/RevolutReader/issues/67), [testing.md § Test-first workflow](../conventions/testing.md#test-first-workflow); 2026-11-09): **measure first, then the code graph.** C8a's apply (Opus 5.5 at xhigh) took each agent to 316k–429k tokens within one chapter of task groups, and its transcripts show what filled them:
- **File reads, a quarter to a half,** mostly whole files read once as models (existing drivers of 14k–29k characters), not repeated reads: the design was read whole once per test-writer, in two calls because the Read tool returns at most about 25k tokens, and by section otherwise.
- **Thinking, about a quarter:** it stays in the context for the agent's whole run (in 522 steps the context never grew by less than the previous call's output), so the effort level sets context size as well as quality.
- **Test output, 0.2–4%:** filtering it saves little.
- **The code graph was never used:** the agents' `tools` lists left out every MCP tool, while the graph server's own start-up hook told every subagent to prefer it, and a worktree was never indexed.
- **Probed** (Claude Code 2.1.321, codebase-memory-mcp 0.9.0): `mcp__codebase-memory-mcp__*` in a subagent's `tools` list gives it the server's tools directly; with `ToolSearch` also listed they turn deferred and need a search first; `disallowedTools` withholds single tools; the server's file watcher picks up files written after the index; a worktree is indexed as a project of its own.
*Setup produces:* both agents' `tools` and `disallowedTools` lines and their "Reading code" rule, the orchestrator's indexing step in the tdd-apply skill (§ 0 step 9), and the paragraph in the testing conventions (inventory: Test-first workflow).
*Generalizes:* before trimming an agent's context, measure what fills it from the transcripts; give agents that write code a symbol-level way to read the code they only model on, and keep whole-file reads for what they change — **reverses** if the next apply's measurement shows the graph's answers costing as much as the files they replace.
