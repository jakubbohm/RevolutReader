# Software Factory — Lessons from RevolutReader

**Status:** knowledge deposit, collected while the project runs · **Started:** 2026-11-04 · **Handover:** not yet ([creating-handover-package.md](creating-handover-package.md))

What the user's future "software factory" (a tool that interviews the owner of a new project and recommends answers from accumulated knowledge) should learn from RevolutReader. The main catalog lives in DoseUp: `D:\source\jakubbohm\DoseUp\docs\software-factory.md`, entries F-1 … F-92 as of 2026-11-04. At the end of the project this file goes into the handover package together with the artifacts it describes ([creating-handover-package.md](creating-handover-package.md)). Where RevolutReader itself runs a cut-down version of a lesson, the project's side (what it gives up, when it switches back) is in [divergences.md](divergences.md).

## What goes in

Only three kinds of entries — everything else is already in the DoseUp catalog:

- **Divergence:** RevolutReader deliberately answered a question differently from DoseUp.
- **Reversal:** RevolutReader reversed one of its own earlier decisions (recording reversals is the factory's best training data — DoseUp F-23).
- **New:** a question DoseUp never faced (e.g., a regulated third-party API with request limits).

Add an entry in the same change or session that makes the decision. The project's own docs stay the authority (ADRs, conventions); an entry here links to them and never replaces them. The default an entry recommends is always the full version, the one that fits a real, long-lived project; a cheaper answer RevolutReader took appears only as an exception, with the constraint that allows it, and gets an entry in [divergences.md](divergences.md).

## RevolutReader's constraint set

Every answer below was reached under these constraints. An entry's *Generalizes* line names the constraint that decided it, so the factory can tell which constraint flips which answer:

solo developer · ~2-month operating period, then decommissioned · **speed of delivery is the top priority** · 3 use cases, essentially one screen · a handful of pre-approved users · read-only access to one real bank account through a regulated third-party API with request limits · Azure, with free-tier resources shared across the owner's projects · one deployed environment.

## Entry format

Same shape as the DoseUp catalog:

```markdown
**R-<n> · <Question, phrased for any project>?** *(<Divergence | Reversal | New> — relates to DoseUp F-<x>, if any)*
Options: <option> · <option> · … (with trade-offs, briefly).
DoseUp: <its answer, one line> — omit for New entries.
RevolutReader (<link to the ADR / convention / progress entry>, <date>): **<the answer>** — <why, briefly>.
*Generalizes:* <the reusable rule> — **and the constraint that would reverse it**.
```

- Ids are `R-1`, `R-2`, … in order of recording, never reused or renumbered. They are shared with [divergences.md](divergences.md): a decision with both a lesson and a divergence keeps the same id in both files, and a new entry in either file takes the next free number.
- Ecosystem facts (versions, prices, limits, licenses) carry the date they were verified.
- Plain language; no RevolutReader-internal codenames without a link.
- Links to the project's files are fine; the handover package carries the reusable ones ([creating-handover-package.md § Inventory](creating-handover-package.md#inventory)).

## Entries

**R-1 · How high is the architecture bar?** *(Divergence — relates to DoseUp F-42)*
Options: architecture first, even at the cost of speed · speed first, but flag works-vs-correct gaps · no explicit rule.
DoseUp: architectural quality is the project's highest priority.
RevolutReader (CLAUDE.md § Working rules, 2026-11-04): **speed of delivery first** — Claude still says when "works" and "correct" differ, then recommends the fastest sound option; the user decides. What the project gives up: [divergences.md R-1](divergences.md).
*Generalizes:* the bar follows the project's "why" (DoseUp F-4): showcase/learning goals buy architecture-first, a short-lived tool buys speed-first. Reverses when the system must outlive its first purpose or others will maintain it.

**R-2 · How does the AI present decisions to the owner?** *(Divergence — relates to DoseUp F-38 and its "propose in prose" rule)*
Options: always a prose proposal · option menus · prose for big decisions, menus for quick ones.
DoseUp: always a prose proposal (solution, trade-offs, alternatives, recommendation); never clickable option menus.
RevolutReader (CLAUDE.md § Working rules, 2026-11-04): **prose for big decisions, menus acceptable for quick confirmations** — the owner asked for a menu-driven review of 40 decisions inherited from DoseUp, with a "more details" option on each.
*Generalizes:* menus are efficient for confirming inherited answers in bulk; new decisions still deserve prose. A picked option is only the closest match — the owner's free-text notes are the owner's words. Reverses toward prose-only when most decisions are new rather than inherited.

**R-3 · Automated releases and changelog?** *(Divergence — relates to DoseUp F-32)*
Options: automated changelog + semver releases · none.
DoseUp: automated changelog, semver tags and GitHub Releases.
RevolutReader (docs/conventions/workflow.md § 3, 2026-11-04): **none** — PRs, squash merge and Conventional Commit titles are kept. What the project gives up: [divergences.md R-3](divergences.md).
*Generalizes:* release automation pays when someone consumes versions; a single-environment app nobody versions against doesn't need it. Reverses when there are consumers of versions (a library, an API with clients, several environments).

**R-4 · Feature flags for trunk-based delivery?** *(Divergence — relates to DoseUp F-33)*
Options: a flag library with a removal task per flag · none.
DoseUp: Microsoft.FeatureManagement; every flag ships with a removal task.
RevolutReader ([docs/conventions/configuration.md § Not adopted](../conventions/configuration.md#not-adopted), 2026-11-04): **none**. What the project gives up: [divergences.md R-4](divergences.md).
*Generalizes:* trunk→prod needs flags only when incomplete work merges. When every change is sized to finish in one session, nothing merges half-done. Reverses when changes span several merges or when releases must be decoupled from deploys.

**R-5 · What stays manual when infrastructure is code?** *(Divergence and Reversal — relates to DoseUp F-53)*
Options: everything manual (guided portal steps) · everything in IaC · IaC with an explicit manual list.
DoseUp: hand-authored Bicep is the only definition of Azure; never portal or ad-hoc CLI.
RevolutReader (docs/conventions/workflow.md § 5, 2026-11-04): **Bicep + Azure Deployment Stacks (removed resources get deleted) for everything the project owns; manual only for what cannot be automated** — subscription access, the Entra application registration, the CD identity's trust (bootstrap), shared resources and access to them, and hand-provisioned secret values. Reversal: the first roadmap draft had made all Azure setup manual; the owner corrected it.
*Generalizes:* ask "which resources outlive or are shared beyond this project?" — e.g., a free tier that exists once per subscription (Cosmos DB) must be shared, so it cannot belong to one project's stack and is referenced as `existing`. Everything project-owned goes into the stack, which also makes decommissioning a single stack deletion. Reverses toward all-manual only for throwaway experiments.

**R-6 · Where do work items live?** *(Divergence — relates to DoseUp F-77, F-79, F-80)*
Options: GitHub issues/milestones/board · plan and status files in the repo.
DoseUp: GitHub issues, milestones and a project board; open decisions as `decision` issues.
RevolutReader (docs/conventions/workflow.md § 9, 2026-11-04): **`pm/roadmap.md` + `pm/progress.md` in the repo**; decisions in ADRs. What the project gives up: [divergences.md R-6](divergences.md).
*Generalizes:* with a fixed plan of ~20 steps, one session per step and a short life, repo files beat a tracker. Reverses with a growing backlog, several contributors, or a need for a board view.

**R-7 · Design mockups before UI work?** *(Divergence — relates to DoseUp F-41)*
Options: a mockup + handoff for every UI-heavy change · only for key screens · none.
DoseUp: every UI-heavy change gets a Claude Design mockup + handoff.
RevolutReader (docs/conventions/workflow.md § 8, 2026-11-04): **one mockup, for the account screen only**. What the project gives up: [divergences.md R-7](divergences.md).
*Generalizes:* the design loop pays per screen; with one real screen, one mockup is enough. Reverses as the number of screens grows.

**R-8 · How do you read a regulated bank API that limits unattended requests?** *(New)*
Options: unattended reads only, within the quota, served from stored data · live reads forwarding the present user's real context, plus a background job within the unattended quota · ask the provider first whether the present user's reads may count as attended.
RevolutReader ([ADR-0001-bank-data-access](../adr/0001-bank-data-access.md), 2026-11-04): **live reads with the signed-in user's real PSU headers when the user opens or refreshes the view; a background job without PSU headers 4 times a day (the PSD2 default for unattended requests, which Revolut counts per account, endpoint and consent); the provider is not asked.** The main user is the owner's daughter, not the account holder the bank treats as the PSU; the owner's position is that she reads on his behalf. The provider's FAQ says to send the headers of whoever triggers the fetch, but not whether that person must be the account holder. Without the provider's explicit confirmation it is an accepted risk: the owner accepts being cut off and keeps the risk low with strict rules on when PSU headers are sent. Stored data refreshed every 6 hours was rejected because the view must match the bank's own app. What the project gives up: [divergences.md R-8](divergences.md).
*Generalizes:* the quota applies only to requests made without the user present, so the "user present" signal must carry the real values of the person actually present, only on requests they trigger directly, never on background work. Whether someone other than the account holder counts as present is the provider's call, not a technical question; without their confirmation it is an accepted risk. Reverses toward asking the provider first, or toward stored data within the unattended quota, when losing access would be costly (long operation, many users, a business) or when the provider's terms explicitly exclude acting on the account holder's behalf. *(Limits verified 2026-11-04 for Revolut via Enable Banking.)*

**R-9 · How do you keep a bank account's transaction history when the bank serves only a rolling window?** *(New)*
Options: show only the bank's rolling window (e.g. 90 days; no database) · store everything fetched · store only settled transactions and re-read pending ones live.
RevolutReader ([ADR-0001-bank-data-access § Decision](../adr/0001-bank-data-access.md#decision), item 6, 2026-11-04): **store only settled transactions, keyed by the aggregator's stable entry reference, from the date the history starts to matter. Read the balance and a short recent window live. Download the older history once, right after an approval.** Revolut returns more than 90 days only within 5 minutes after an approval. Pending transactions can still change, be cancelled, or get a new ID once settled. The rolling window was rejected because the owner needs the history from a fixed date for good.
*Generalizes:* settled transactions are immutable facts worth storing; pending ones are a live view, never stored. Capture older history in the window right after an approval, because it may not come back without the account holder present. Before choosing, ask the owner from which date the history matters: a fixed start date that is about to fall out of the window makes it urgent. Reverses toward the rolling window when nobody needs history older than the bank serves, which also removes the database. *(Revolut and Enable Banking behaviour verified 2026-11-04.)*

**R-10 · How do you keep a short-lived app restorable after it is decommissioned?** *(New)*
Options: nothing (decommissioning is final) · write a rebuild guide at the end · keep a register of every expiring approval and secret from the first step, and write the rebuild guide from it before decommissioning.
RevolutReader ([docs/operations/expiring-approvals.md](../operations/expiring-approvals.md), roadmap D1, 2026-11-04): **a register of every expiring approval and secret with its expiry, how you notice and how to restore it, kept current by every step that creates or renews one; plus a reinstatement guide written before decommissioning**, assuming every secret, approval and cloud resource is gone. The owner expects to reactivate the app later. Stored transactions are not exported at decommissioning: a reinstated app downloads the history again in the 5 minutes after its new approval. Third-party approvals with short, fixed terms (here a 30-day account link and a 180-day bank session) are easy to forget and need the account holder present to renew.
*Generalizes:* collect restore knowledge as you go, because reconstructing it at the end misses the hand-made steps. For each external approval, record who must be present to renew it and what data can be recovered afterwards (here, older transaction history only right after a new approval). Reverses toward "nothing" only when the app will certainly never return. If it is torn down, decide before deletion whether to export the data that cannot be fetched again.

**R-11 · How does a personal app get read access to the owner's own bank account without a banking licence?** *(New)*
Options: become a licensed account information provider (not realistic for an individual) · a commercial contract with a bank-data aggregator (company verification, volume-based pricing with a monthly minimum) · the aggregator's free mode for the owner's own accounts · unofficial screen scraping or shared bank credentials (against the bank's terms, fragile, unsafe).
RevolutReader ([ADR-0001-bank-data-access § Context](../adr/0001-bank-data-access.md#consent-validity-and-pricing-q5), [spikes/enable-banking/README.md](../../spikes/enable-banking/README.md), 2026-11-04): **Enable Banking's restricted production mode.** A production application becomes active once the owner links their own account in the Control Panel. It is free, limited to linked accounts, and allowed "solely for evaluation purposes or for the personal use of private individuals"; the Control Panel account must belong to the account holder. Costs accepted: registration still demands a privacy URL, a terms URL and a data protection email (placeholders work, since restricted mode does not check them); the account link lasts only 30 days and needs the account holder in the bank app to renew (roadmap M9); and data access still needs its own API session, up to the bank's maximum (180 days for Revolut).
*Generalizes:* for a personal or family tool reading the owner's own accounts, look for the aggregator's personal-use or own-accounts mode before anything commercial. Check three things first: whose accounts it covers, how long each approval lasts and who must be present to renew it, and the bank's request limits. Reverses toward a commercial contract when the app reads other people's accounts, serves customers or earns money. *(Enable Banking terms, FAQ and behaviour verified 2026-11-04.)*

**R-12 · Does the acceptance-test harness run the app inside the test process, or as the real running app?** *(Divergence — relates to DoseUp F-26)*
Options: in-process test host (WebApplicationFactory; the test replaces dependencies directly) · containers per dependency (Testcontainers) · the real running app, started by the orchestrator (Aspire testing harness).
DoseUp: Aspire harness only — the real graph of processes; tests that need to move the clock stay at unit level, because a fake clock cannot reach another process.
RevolutReader ([docs/conventions/testing.md § Acceptance-test harness](../conventions/testing.md#acceptance-test-harness-the-app-runs-inside-the-test-process), 2026-11-04): **in-process (TUnit.AspNetCore), as a project-only exception; the factory default stays DoseUp's real running app.** What the app reacts to lives outside it, and the tests must control it: the bank (to check which headers the app sends and that the background job stays within 4 calls a day), the clock (a check 4 times a day) and the sign-in key. In-process, each is a one-line swap, and no test needs a real secret. The app is a single API process. What the project gives up: [divergences.md R-12](divergences.md).
*Generalizes:* DoseUp's default stands. Run in-process only as an exception, for a single-process app whose behaviour depends mostly on the clock and on third parties the tests have to fake anyway. Reverses to the default when the app runs as several processes whose wiring is itself a risk, or when the tests need no control over the clock or third parties.

**R-13 · How do tests fake a third-party bank API when the bank has no sandbox?** *(New — relates to DoseUp F-86)*
Options: an in-memory fake of our own client · a local fake HTTP server with responses typed from the docs · the same local fake server with responses copied from the provider's hosted mock bank · the hosted mock bank as a dependency of the CI suite · recording the real account (bank data in the repository; never).
RevolutReader ([docs/conventions/testing.md § Fake bank](../conventions/testing.md#fake-bank-a-local-fake-server-in-front-of-our-real-enable-banking-client), [spikes/enable-banking-mock/](../../spikes/enable-banking-mock/README.md), 2026-11-04): **every automated test runs our real client against a local fake server (WireMock.Net) whose responses are copied from Enable Banking's hosted Mock ASPSP (made-up data); the hosted mock serves response captures, on-demand checks of the real client against the real API, and local development; no CI job against it.** The hosted mock returns exactly what you enter, changes show up live, and its errors are the real API's. But entering data and approving a session both need the owner's Control Panel login (its internal API refuses unauthenticated calls), every test would share one data set, and it cannot reproduce the bank's limits (no 429; Revolut allows 4 unattended requests a day, the mock any number). The rules worth testing (which headers are sent, how many calls a day) are visible only in the requests, which only a local fake server records. What the project gives up: [divergences.md R-13](divergences.md).
*Generalizes:* fake the third party locally in every automated test, and treat the provider's hosted mock as the source of truth for response shapes, not as a test dependency. Before relying on a hosted mock, check three things: whether test data can be set up by an API without a personal login, whether it reproduces the provider's limits and errors, and whether the approval step can run unattended. Reverses toward an opt-in CI contract job against the hosted mock (a stored sandbox session and key as low-risk CI secrets, data set up once) when the system lives long enough for provider API drift to matter, and toward the hosted mock in more places when it offers a data and error-simulation API. *(Enable Banking Mock ASPSP behaviour verified 2026-11-04.)*

**R-14 · Which test kinds beyond unit, integration and acceptance does a short-lived app skip?** *(Divergence — relates to DoseUp F-27, F-28, F-29)*
Options, each adopted, deferred or skipped: mutation testing (Stryker) · architecture tests (ArchUnitNET) · browser end-to-end tests (Playwright).
DoseUp: ArchUnitNET enforcing the written dependency rules; @playwright/test with a smoke subset on PRs and the full suite nightly; mutation testing after a spike, nightly, never a PR gate.
RevolutReader ([docs/conventions/testing.md § Defaults](../conventions/testing.md#defaults), 2026-11-04): **none of the three.** Little domain logic and Stryker.NET's TUnit support still in preview (its Microsoft Testing Platform runner, since March 2026); the test-first close step runs mutation testing only if it is configured. One API project with few layers, whose few structural rules are enforced by banned-API analyzers and an ordinary test. No browser tests, because each scenario is verified at one level (R-19). What the project gives up: [divergences.md R-14](divergences.md).
*Generalizes:* each pays off with size and lifetime. Mutation testing pays when rules are dense and tests are written by agents: it is the automated form of "could a dumb implementation pass these tests?" (R-17). Architecture tests pay when several projects or modules have boundaries that erode. Browser end-to-end tests pay with several screens and a long life. Reverses for any of them when its condition appears.

**R-15 · How do spec-tool scenarios become executable specifications?** *(New)*
Options: tests written after the code from the spec, by the same agent · Gherkin `.feature` files with step bindings (Reqnroll, cucumber-js) · an internal DSL in the code's language, Farley/LMAX style: test case → DSL → protocol driver → system under test, one test per scenario, linked by an attribute and a traceability check.
RevolutReader ([docs/conventions/testing.md § Acceptance tests](../conventions/testing.md#acceptance-tests-executable-specifications), [§ Every scenario has exactly one test](../conventions/testing.md#every-scenario-has-exactly-one-test-the-traceability-check), 2026-11-04, from the owner's design session of 2026-10-22): **the internal DSL in C#; every OpenSpec scenario has exactly one test, claimed by `[Scenario("<capability>", "<name>")]`; a traceability test in the normal suite fails the build on a missing, duplicate or stale claim; the test-case layer is the spec, so changing it needs the owner's approval.** Gherkin was rejected: the spec scenarios already are the readable Given/When/Then, and `.feature` files would be a second copy plus binding glue, two sources of truth. Gherkin pays only when non-developers write the scenarios. Supporting rules: the DSL gives every test unique names (aliasing), so tests never share or clean data and run in parallel; drivers remember earlier steps, so test cases pass no IDs; a test case that would change if the channel changed (UI vs API) is in the wrong layer; edge-case combinations belong in unit tests; the harness comes once, as a walking skeleton (one trivial scenario green end to end) before the first feature. Expected results are always written by hand: snapshot (approval) testing was rejected because the expected value would come from the code, which defeats test-first (DoseUp rejected it for a different reason, ceremony). `tasks.md` becomes the test list: groups `[acceptance]` → `[unit] <component>` → `[integration] <port>` → `[wiring]` → `[close]`, one behaviour per task phrased like a test name, never a "write tests" task; changes with more than 3 scenarios are sliced per scenario after all acceptance tests are written.
*Generalizes:* the spec tool's scenarios are the readable layer; the executable layer must be code the compiler and refactoring tools understand, and a machine check, not discipline, keeps the two from drifting apart. Reverses toward Gherkin only when non-developers author the scenarios themselves.

**R-16 · How do you stop an AI agent from writing tests that just mirror its own code?** *(New)*
Options, weakest to strongest: rules in the spec tool's apply guidance ("write the test first, show the failure output") · a hook that blocks edits outside red-green-refactor (TDD Guard: no .NET reporter as of 2026-10; its successor Probity claims any language, unverified) · two sessions, "all tests red" then "all green" · an orchestrator with a test-writer and an implementer subagent in separate contexts, looping per task group · agent teams (peers messaging each other).
RevolutReader ([docs/conventions/testing.md § Test-first workflow](../conventions/testing.md#test-first-workflow), [`.claude/skills/tdd-apply/`](../../.claude/skills/tdd-apply/SKILL.md), 2026-11-04, designed 2026-10-22): **the orchestrator with two persistent subagents, the full setup even for a small app, because building the convention is worth more than speed on its first use.** The orchestrator plans, delegates, verifies and judges; it never edits tests or code. All acceptance tests are written first and reviewed by the owner (the most valuable human checkpoint: it checks how the spec was translated); then, per task group (one component), the test-writer writes failing tests and compile-only stubs, the orchestrator verifies they fail at runtime and commits, the implementer makes them pass, and the orchestrator verifies the suite and that the diff since the red commit touches no test file. Rejected along the way: batching all unit tests first (unit tests are coupled to design-level APIs that shift during implementation, so it deadlocks or floods disputes, loses the feedback loop, and "red for the right reason" cannot be checked on a wall of failures); making the test-writer and implementer skills (a skill runs in the caller's context, which is exactly what must be separated; conventions can still be preloaded into an agent as a skill); agent teams (peer-to-peer messaging defeats the orchestrator as arbiter, and costs more); banning the agents from reading each other's work (the implementer must read the tests, they are its spec; the test-writer needs real types; with test-first ordering the code under test does not exist yet). Mechanics that matter: subagents are resumed with SendMessage (no experimental flag needed, verified 2026-11-04) and their IDs kept in a state file, because the orchestrator's own context may be compacted; artifacts stay the source of truth when an agent is lost; one working tree, no worktree isolation (it breaks resuming); disputes follow a fixed authority (behaviour → spec, API shape → design, test quality → test-writer), the orchestrator forwards only the claim and the spec excerpt, never the implementation, and a second identical dispute goes to the owner, whose answer lands in the spec; a hook on the implementer blocks test edits as a second layer, while the git diff check is the one to rely on; the owner also reviews every group's tests on the first changes (`review=all`) to calibrate the test-writer. The kit from the design session committed only after green, so its diff check mixed the test-writer's and the implementer's changes; committing at every handoff fixes that (R-21). For slow builds (from the same session, for a project whose build takes 5+ minutes): the inner loop never builds the solution, only the component's test project with a filter; test projects must not reference the host; the orchestrator verifies once per handoff and never while an agent is building; the agent shell timeout must exceed the build (Claude Code's default is 2 minutes; verify the setting names at setup).
*Generalizes:* separate contexts are what stop mirroring; rules and hooks only slow it down. Verify every report yourself, by running the tests and checking the diff. Batch only the tests that are decoupled from the design (acceptance); alternate per component for the rest. Reverses toward plain apply rules for throwaway prototypes, and toward fewer human gates once the test-writer is calibrated.

**R-17 · What should the implementer agent be told about how much code to write?** *(Reversal — within the design session of 2026-10-22)*
Options: classic TDD, "write the dumbest code that passes" (fake it, triangulate) · "write production-quality code" with no scope limit · production quality, but only the behaviour the failing tests require.
RevolutReader ([docs/conventions/testing.md § Test-first workflow](../conventions/testing.md#test-first-workflow), [`.claude/agents/implementer.md`](../../.claude/agents/implementer.md), 2026-11-04): **How: production quality, the real implementation per the design and conventions, no hardcoded results, no shortcuts. What: only the behaviour the failing tests ask for; if more seems needed, don't code it and don't drop it, report it as a missing test.** The first draft carried "dumbest code that passes" over from hand-driven TDD; the owner questioned it, and it was dropped: tiny steps and emergent design are human reasons, while with agents the design is already in `design.md`, and writing throwaway code just burns turns. The owner then saw "production quality" and "no behaviour without a test" as contradictory; the rule was reworded into How and What, because the typical agent failure is writing too much (extra validation, parameters, "while I'm here" features), and untested behaviour is where spec and code drift. Bug guards (null checks) count as quality; expected states (a Result value such as "the bank is busy") are behaviour and need a test. Examples where "good practice" harms here: a retry on the bank's 429 burns the 4 unattended requests a day; returning more fields than the UI shows breaks the exact-shape rule and exposes bank data. The "dumb implementation" idea survives as a test-quality check: could a hardcoded return pass these tests? Mutation testing automates exactly that question.
*Generalizes:* give an agent a scope rule, not a style rule: production quality inside the scope the tests define, with a defined path (report a missing test) for anything outside it. Reverses only for a human doing TDD by hand.

**R-18 · Where do integration tests go in an agentic test-first workflow?** *(Reversal — within the design session of 2026-10-22)*
Options: none (acceptance tests cover the wiring) · port contract tests for every port, written first · split by kind: contract behaviours first, adapter internals after.
RevolutReader ([docs/conventions/testing.md § Integration tests](../conventions/testing.md#integration-tests), 2026-11-04): **port contract tests only for behaviours the design states for a port (concurrency, idempotency, failure modes), written first by the test-writer and run against both the in-memory fake and the real adapter, so the fake the unit tests rely on stays honest; happy-path persistence and glue are left to the acceptance tests; adapter edge cases (a migration on existing data, a tricky query, serialization quirks, error-response handling) are written after the implementation by the implementer, in a folder it may write to.** The first answer put contract tests, including round trips, before the implementation for every port; the owner pointed out that adapter tests depend on the implementation chosen, so the rule was split by kind and the round-trip tests were dropped. Most changes therefore have no integration group. In RevolutReader the bank client gets no in-memory fake unless a unit test needs one, so contract tests are rare.
*Generalizes:* test first what the design decides (the port's contract); test after what the implementer decides (the adapter's internals); let acceptance tests cover the plain wiring. Reverses toward more contract tests when many handlers are unit-tested against fakes of the same port.

**R-19 · At which level is a UI scenario verified?** *(New)*
Options: (a) scenarios describe only the API; display rules move to the design and frontend tests, outside the spec · (b) one level per scenario: an API acceptance test by default, a frontend component test for rules only the browser shows, "manual at handover" for device-only behaviour, all three claimed for the traceability check · (c) the full Farley version: one C# test per scenario, run through an API driver or a browser driver (Playwright) against the real running app.
RevolutReader ([docs/conventions/testing.md § Every scenario has exactly one test](../conventions/testing.md#every-scenario-has-exactly-one-test-the-traceability-check), 2026-11-04): **(b); (c) is the factory's default.** Frontend rules (formatting, empty states) are testable on components with Vitest, faster and simpler; device behaviour (a push notification on an iPhone, adding the app to the home screen) needs the real phone anyway, at the handovers. (c) would need browsers in CI, the app on a real port (against the in-process harness, R-12), the built frontend served, and a sign-in without the real identity provider, likely test-only frontend code: too much for one screen and two months. What the project gives up: [divergences.md R-19](divergences.md).
*Generalizes:* in a long-lived app with several screens, (c) keeps one source of truth per scenario, catches integration breaks, and its setup cost is paid once. (a) silently drops screen behaviour from the spec. Reverses from (b) to (c) as screens and lifetime grow, or when integration breaks between frontend and API actually happen.

**R-20 · How does an owner who does not read long AI-written artifacts still own the spec?** *(New)*
Options: read every artifact in full · read nothing and trust the tests · short human-readable summaries plus a fixed reading routine.
RevolutReader ([`openspec/config.yaml`](../../openspec/config.yaml) rules, [docs/conventions/testing.md § Your reading routine](../conventions/testing.md#your-reading-routine-about-5-minutes-per-change-after-propose-before-apply), 2026-11-04, designed 2026-10-22): **the proposal starts with a TL;DR (about 8 lines: what and why, out of scope, the riskiest assumption, the scenario names added, changed and removed); the design starts with a TL;DR (about 10 lines: key decisions with reasons, new interfaces one line each, integration points, anything hard to reverse); specs get no TL;DR, because an extra section could interfere with merging delta specs on archive, so scenario names must work as a checklist on their own, each scenario 3–6 lines; a 5-minute routine after propose: proposal TL;DR, the list of scenario names (missing scenarios are the most common and most expensive problem), only the risky scenarios in full, design TL;DR.** The acceptance-test review becomes the second check, not the first. Reading nothing was rejected: if no human reads the spec, every downstream test only checks the agent's interpretation against itself. Known risk: a TL;DR can drift from its body, and tests follow the body; a mismatch is the signal to read the full artifact.
*Generalizes:* the owner's attention goes to scope and to the list of scenario names, not to prose; ask agents to write the summary last and keep it in sync. Reverses toward full reading for high-stakes or regulated changes.

**R-21 · How does the commit history show which step of an agentic change each commit belongs to?** *(New)*
Options: free-form messages · a commit only per finished task group · a commit at every handoff, tagged with the workflow step inside Conventional Commits, or as a git trailer.
RevolutReader ([docs/conventions/workflow.md § 3](../conventions/workflow.md#3-git), 2026-11-04): **a commit at every handoff, `<type>(cNNN): [<step>] <summary>`, with the steps `[plan]`, `[accept]`, `[red]`, `[green]`, `[wire]`, `[close]`, `[archive]`; the orchestrator holds the owner's standing permission to commit on the change branch only (never push, never `main`).** The owner proposed prefixes per spec-tool command (explore, apply-tests, apply-implement); steps were chosen instead, because explore and verify produce no commits and apply has a red-green pair for every task group. The real reason is mechanical: committing the test-writer's red tests before the implementer starts makes "the green step changed no tests" a plain diff. Squash merge collapses the commits on `main`; the repository's squash message setting keeps the list in the commit body.
*Generalizes:* in an agent workflow, commit at every change of hands; it turns the rules between agents into checkable diffs and makes the human gates visible in history. Reverses toward one commit per task when a single agent does both test and code.

**R-22 · How does a project pass what it learned on to the software factory?** *(New and Reversal — reverses this file's first handover procedure)*
Options: copy the lesson entries as text into the factory's catalog · keep copies of the reusable artifacts next to the lessons · a handover package built at the end: the lessons plus the reusable artifacts themselves, taken from an inventory kept current while the project runs.
RevolutReader ([creating-handover-package.md](creating-handover-package.md), 2026-11-04): **a handover package built at the end of the project: the lessons, plus the artifacts listed in an inventory that every step keeps current, cleaned of project specifics, secrets and bank data, with a README naming the target. The receiving side takes it in through its own process.** The first procedure copied the lesson entries into DoseUp's catalog as new entries. The owner pointed out that the reusable work lives in artifacts (the test-first workflow alone is a convention, a skill, two agents, a hook and the spec tool's rules), and copies of them next to the lessons would drift from the originals.
*Generalizes:* a lesson describes the answer; the artifact is what the next project reuses, so hand over both. Collect the inventory as you go, because reconstructing it at the end misses things (as with restore knowledge, R-10). The receiver integrates the package under its own rules. Reverses toward text-only lessons when a project produced no reusable artifacts.
