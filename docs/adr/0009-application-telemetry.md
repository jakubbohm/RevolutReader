# ADR-0009: Application telemetry — Application Insights on the log workspace, fed by the app with its own identity

**Status:** Accepted (the user's decisions, 2026-11-07 and 2026-11-08) · **Date:** 2026-11-08 · **Roadmap:** C4, C11; applied in C11; supersedes the daily cap in [ADR-0006-hosting-registry-and-job § Consequences](0006-hosting-registry-and-job.md#consequences) (C4) · **Questions:** none

> The design trail: [c006 design.md D8 (b), D9, D10, D12, D13](../../openspec/changes/c006-harden-bank-adapter/design.md); the workspace: [c005 design.md D6](../../openspec/changes/archive/2026-11-07-c005-add-deployment-pipeline/design.md). Sources were read on the dates given with each one.

## Context

- **The app scales to zero.** A copy that stopped takes its output with it, and the live log stream shows only running copies ([Microsoft Learn: log options](https://learn.microsoft.com/en-us/azure/container-apps/log-options), updated 2026-08-21, read 2026-11-06). So C4 made a Log Analytics workspace, `log-revolutreader`, the environment's log destination, with 30 days of retention and a 0.1 GB daily cap, and left Application Insights for later, "if C7 needs it" (c005 design.md D6).
- **What the workspace showed (2026-11-07):** the app's console output in the default text format, two output lines per entry, each stored as its own row in `ContainerAppConsoleLogs_CL`. Level and category sit on another row than the message, and no field is a column. A failed bank read was hard to find, and early in operation every unexpected answer from the bank should be easy to find, to catch the cases nothing handles yet (c006 design.md D8).
- **The platform's own metrics, free:** the Container Apps metrics page shows requests, error requests, response time, replicas, CPU, memory and network. They are Azure Monitor platform metrics, outside the workspace and its allowance (c006 design.md D10).
- **The free allowance (read 2026-11-08):** the first 5 GB a month per billing account of Analytics Logs ingestion are free ([Azure Monitor pricing](https://azure.microsoft.com/en-us/pricing/details/monitor/)). Workspace-based Application Insights is billed by the workspace that holds its data ([Microsoft Learn: Azure Monitor Logs cost calculations](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/cost-logs), updated 2026-09-02), and the pricing page names no separate grant for it, so its data counts against the same 5 GB. Included retention: 31 days for Analytics Logs, 90 days for Application Insights data. A daily cap stops collection with a short delay, so some overshoot is billed ([Microsoft Learn: daily cap](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/daily-cap)).
- **Three ways in for a .NET app on Container Apps (read 2026-11-07):**
  - Microsoft's Azure Monitor exporter for OpenTelemetry, `Azure.Monitor.OpenTelemetry.Exporter` (1.10.0, stable), added to the app's own OpenTelemetry setup ([readme](https://learn.microsoft.com/en-us/dotnet/api/overview/azure/Monitor.OpenTelemetry.Exporter-readme));
  - the Container Apps managed OpenTelemetry agent, announced generally available in May 2025; its Learn page, updated 2026-06-04, still says "preview" in the description ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/container-apps/opentelemetry-agents));
  - the Microsoft OpenTelemetry Distro, `Microsoft.OpenTelemetry` 1.2.0 (first stable in May 2026), Microsoft's headline recommendation for new apps, with live metrics, the profiler and sampling, built on the same exporter ([Enable OpenTelemetry in Application Insights](https://learn.microsoft.com/en-us/azure/azure-monitor/app/opentelemetry-enable?tabs=aspnetcore), updated 2026-10-09; [NuGet](https://www.nuget.org/packages/Microsoft.OpenTelemetry)).
- **The app's telemetry setup before C11:** ServiceDefaults configures OpenTelemetry with ASP.NET Core and HTTP-client instrumentation, and a filter keeps the bank's requests, whose paths carry the account id, out of the traces ([c004 design.md D5](../../openspec/changes/archive/2026-11-07-c004-add-enable-banking-adapter/design.md)). It exports only locally, to the Aspire dashboard.
- **Request telemetry records the user's browser:** OpenTelemetry's ASP.NET Core instrumentation puts each incoming request's browser (`user_agent.original`) on its server span, so exported request traces carry the users' browser names.

## Decision

Decided by the user: item 1 in C4 (2026-11-06, c005 design.md D6); items 2 and 4 on 2026-11-07, with the identity's role step by hand confirmed on 2026-11-08; items 3, 5 and 6 on 2026-11-08.

1. **The Log Analytics workspace `log-revolutreader` is the environment's log destination** (from c005 design.md D6): the app's console output and the platform's events about it. The console output stays as the safety net for a failure at start, before OpenTelemetry runs.
2. **Application Insights `appi-revolutreader`, workspace-based on that workspace,** receives the deployed app's telemetry through Microsoft's Azure Monitor exporter in the app's own OpenTelemetry setup (ServiceDefaults). It only adds a destination: the instrumentation and the filter that keeps the bank's requests out of the traces stay as they are. The exporter is added only when the Application Insights connection string is set, so only the deployed app exports to Azure; local runs (the Aspire dashboard) and the tests are unchanged.
3. **Logs and traces only, not the app's metrics.** Traces give every request as a row in `AppRequests` (route, status, duration, exception); the bank adapter's one log line per read gives the bank reads (outcome, status, error code, reason, duration); the platform's metrics cover the rest. The app's own metrics stay local.
4. **Written with the app's managed identity:** local authentication is off on Application Insights, and the app's user-assigned identity, `id-revolutreader-app`, holds Monitoring Metrics Publisher on it, created by the deployment stack like the identity's Key Vault role. The connection string then only says where to send.
5. **The workspace's daily cap matches the free allowance: 0.16 GB a day** (5 GB ÷ 31 days), up from 0.1 GB. It covers the Application Insights tables, which live in the workspace; the Application Insights resource keeps its own default cap. Retention stays 30 days for the workspace, and the Application Insights tables follow it.
6. **What the private telemetry may hold.** Application Insights and the workspace can be read only through the owner's Azure access. They may hold personal data that helps diagnosis, such as the users' browser names in request telemetry, so request traces are exported unchanged. They never hold secrets, and never bank data (balances, amounts, counterparties, transaction texts) or account identifiers (CLAUDE.md; c004 design.md D5 and its telemetry guard). **Nothing personal goes anywhere public:** the repository's files, PRs, issues, GitHub Actions logs (public, since the repository is) and spike evidence. In the user's words: "I don't need to have my personal data stripped out from the Azure Application Insights, as those are only visible and accessible to me."

## Alternatives considered

- **JSON console output instead of Application Insights** (`Logging__Console__FormatterName=json`, tried in a scratch app on .NET 11 RC3): one JSON line per entry, with the fields and the exception inside, and no new resource. But every query unpacks the JSON from a text column, and requests, exceptions and log lines are not linked.
- **The Container Apps managed OpenTelemetry agent:** no code change, since ServiceDefaults already exports OTLP when the agent's address is injected. But Application Insights receives no metrics through it, it runs as one copy with no health signal, and it requires Application Insights to accept the connection string's key (local authentication on). Claude first recommended it for needing no code change; the user chose the mature path once both were shown.
- **The Microsoft OpenTelemetry Distro:** it installs its own HTTP-client tracing with its own filter, which would collide with the filter that keeps the account id out of traces, and one small app needs none of its extras.
- **The connection string's key for writing,** instead of the app's identity: no manual step, but anyone holding the connection string could send telemetry.
- **All three signals,** metrics included: the more complete default for a long-lived app. The app's metrics add .NET internals (garbage collection, heap size, thread pool, exception counts) and per-minute sums by route, which matter when hunting a leak or a slowdown inside the app; unlikely for an app that runs minutes at a time for one user. Switching them on later is a one-line change in ServiceDefaults.
- **Stripping the browser from exported traces** (Claude's lean, for consistency with c004 design.md D5): not needed for data only the owner can read, and it would hide which device made a request.
- **Allowing bank data in private telemetry as well** (the user's first thought): private logs leak through copying (into public issues or PRs, AI transcripts) and through anything with read access (the deploy identity, Contributor on the resource group, can query the workspace); OWASP's logging guidance and GDPR data minimisation advise against it; and one configured account gains nothing from its id in a log. It would also have changed CLAUDE.md, c004 design.md D5 and its guard.

## Consequences

- **The deploy identity's fifth role:** the condition on its Role Based Access Control Administrator role lists the roles it may assign, and Monitoring Metrics Publisher was added by hand before C11's merge ([azure-prerequisites.md](../operations/azure-prerequisites.md), item 5). Without it, the deploy fails at the new role assignment and the previous revision keeps running. The widened condition stays until someone narrows it by hand, also after a revert.
- **Two settings,** `APPLICATIONINSIGHTS_CONNECTION_STRING` and `AZURE_CLIENT_ID`, under their standard names, empty in `appsettings.json` and written by Bicep from the resources ([configuration.md § Telemetry settings](../conventions/configuration.md#telemetry-settings)). Neither is a secret. The app refuses to start when the connection string is set without the client ID. Azure.Identity's default credential also picks up `AZURE_CLIENT_ID` by itself, so C6's storage access could use the same identity without more wiring.
- **The volume:** a reached cap stops all collection, the console output included, until the workspace's daily reset. [#17](https://github.com/jakubbohm/RevolutReader/issues/17) checks the real ingestion in the first days. The allowance belongs to the billing account, so any other workspace on it would share the 5 GB.
- **Finding failed bank reads:** the ready queries in [deployment.md § Checks](../operations/deployment.md#checks), against `AppTraces`; their columns are confirmed with C7's first bank lines. Alert rules are left for later: the queries come first.
- **Not adopted:** sampling, live metrics, the profiler.
- **The telemetry guard** (c004 design.md D5) checks what the app exports through the same pipeline, whatever the destination. For bank reads it also keeps the present user's browser out, stricter than item 6 needs; it stays.
- **Rollback:** reverting C11 makes the stack delete Application Insights (telemetry already written stays in the workspace until its retention ends) and returns the cap to 0.1 GB; the widened condition stays, harmless.
- **ADR-0006-hosting-registry-and-job § Consequences:** its log destination stands; its 0.1 GB cap is superseded by item 5.
- **Software factory:** [lessons.md R-53](../software-factory/lessons.md) (reversing the deferral in R-49) and [R-54](../software-factory/lessons.md); the project's cut-down version in [divergences.md R-53](../software-factory/divergences.md).
