## Decided on the user's behalf

(O adds one line per decision during the unattended run.)

1. **Task 34.1's behaviour built early** (group 16): a failed page ending the read came out of `TransactionPages.ReadAll` because the union switch must handle every case. Why: the alternative is an artificial throw. T still writes 34.1's test; it is expected to pass at once. Where: § Disputes and decisions, group 16.
2. **An empty key passed straight to `ReadTransactionPage` is sent as `continuation_key=`** (group 17); only `ReadTransactions` stops on it (16.6). Why: no caller other than Check 2 calls the page reader, and Check 2 stops on an empty key itself. Where: § Disputes and decisions, group 17.
3. **An IPv4 address in IPv6 form (`::ffff:203.0.113.7`) is sent to the bank as given** (group 19); turning it into plain IPv4 is left to C7, which sets up the forwarded headers. Why: Enable Banking accepts valid IPv6, and the address comes from C7's code. Where: design.md D2 (heads-up for C7).
4. **A user agent with characters HTTP cannot carry gets no check of its own** (group 19). Why: C7 takes the user agent from the incoming request, where a line break cannot occur; C7 confirms the rest. A check now would guard a case no caller has yet. Where: design.md D2 (heads-up for C7).
5. **Error codes are matched exactly as the API reference writes them** (group 23); `expired_session` is an unknown code, so unexpected. Why: the reference defines upper-case codes; guessing other spellings would hide a changed answer. Where: design.md D4.
6. **A blank `error` code counts as no code** (group 23, for group 29): the HTTP status decides. Why: the same reasoning as your option A for an empty continuation key: an empty string cannot name a code. Group 29's "without an error code" tests take null, empty and blank. Where: design.md D4.
7. **`BankErrorKind` lists `Unexpected` first** (group 23): a code path returning the enum's default would then throw rather than tell the user the bank link expired. Why: fail safe; the type is internal to the adapter. Where: design.md D4 and § Public API sketch.
8. **Unreadable success answers become `BankReadException` in group 24, with edge tests in `Wiring/EnableBanking/`**: a body that is not JSON, a missing `balances` or `transactions` list, a transaction without an amount. Why: the implementer flagged since group 5 that these throw other exceptions, and D4 already says an unparseable body is a `BankReadException` (no new rule, only its tests); edge cases of the adapter belong in `Wiring/` (testing.md). Where: tasks.md 24.3 note, this file § Disputes and decisions.
9. **The JSON reading stays lenient; each reader checks what it reads** (group 24, the implementer's choice, accepted). Why: strict null handling in the serializer would fail a read on a malformed *cancelled* transaction, against your group 14 decision (D3: left-out transactions are only counted). Extended after group 24: a missing currency or a null payment-details line on a kept transaction or the balance is a `BankReadException` too. Where: `EnableBankingClient`'s JSON options comment; edge tests in `Wiring/EnableBanking/UnreadableAnswerTests.cs`.
10. **The fake bank's expired session answers 422** (group 24). Why: the API reference pins no status; every error the Mock ASPSP answered was 422, and design.md D4 cites 422 for session errors. The classification goes by the code, so the status does not change the outcome. Where: `BankDriver.ReportsExpiredSession` comment.
