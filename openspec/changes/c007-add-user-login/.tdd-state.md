## Disputes and design gaps

- 2026-11-08, before slice 1 (found by O): the fallback policy also applies to requests that match no endpoint, so
  anonymous `GET /api/no-such-address` would answer 401, breaking api-errors' 404 scenario. The user chose: run
  `UseAuthorization` only when an endpoint matched (`UseWhen`). Recorded in design.md D3 (`[plan]` commit f1fa8e6).
  At slice 1, I found `UseWhen` alone lets WebApplication add its own unconditional authorization step; I first
  suppressed it with ASP.NET's internal property name. O chose ASP.NET's documented hook instead: the result handler
  `UnmatchedRequestsPass` (same behaviour), [plan] 9e580d5.
- 2026-11-08, slice 1 review (wf_703e804b-cf5, confirmed minor): a write to an unknown address lands on the router's
  405 rejection endpoint (no metadata → fallback policy), so anonymous callers got 401, signed-in 405; writes answered
  405 since C3 against api-errors' 404. The user chose: fix it in this change, and approved the new api-errors scenario
  "A write to an unknown API address answers with a problem description". Plan: `ApiNotFound` (`/api/{**path}`, every
  method, anonymous, 404) + `UnmatchedRequestsPass` treats non-RouteEndpoint as unmatched; tasks groups 3a–3d.
